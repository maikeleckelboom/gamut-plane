# 0002: vNext instrument architecture

Status: accepted direction for vNext; not implemented in v0.3

## Context: the released v0.3 baseline

The released architecture is described in [Architecture](../architecture.md) and [ADR 0001](0001-coordinate-plane-projections.md). Core owns the authored `ColorValue`, observation, exact gamut analysis, explicit mapping, output policy and two editable coordinate planes. Render shares Canvas rendering, sampled guide data and pure presentation calculations. Vue and native React each assemble a complete instrument, own interaction lifecycle and ship a separate local stylesheet. The standalone Vue app adds gamut controls, output and inspection around that instrument. The current picker edits OKLCH and OKLab, checks sRGB and Display P3, and has one `boundaryTarget` independent of two guide-visibility flags. These are current capabilities, not the vNext model.

vNext reforms this product without rejecting its proven behavior. The existing release remains the pre-vNext baseline against which extraction and later changes are judged.

## Decision

### Product and color authority

- **Popover-first instrument.** The canonical product is one compact reusable instrument. Its complete ordinary picking experience must fit comfortably in a roughly 430–480px desktop popover host and remain usable on mobile. Standalone demos and playgrounds host that same instrument; they must not gain an exclusive, more capable product UI. The default visible order is compact instrument controls, the plane, channel controls immediately after the plane, then concise authored-color/output state. Advanced capability is progressively disclosed rather than permanently arranged as an inspector or dashboard. This sets hierarchy, not final dimensions or component composition.
- **One authored color.** One `ColorValue` remains authoritative. It can be authored in one representation, observed through others, checked against gamuts, serialized in several forms or explicitly mapped. Observation, active coordinate-system changes and visualization changes never silently redefine its authorship. A deliberate edit may create a new definition; conversion for viewing does not. Preserve defining-representation identity, missing/powerless-coordinate semantics, alpha and other current `ColorValue` rules until an explicit later decision supersedes them.
- **Many precise representations.** The domain and UI must grow beyond a closed `OKLCH | OKLab` view switch to dozens of justified color spaces, models and encodings over time. Candidates include OKLCH, OKLab, CIE Lab/LCH, XYZ variants, sRGB and linear sRGB, Display P3 and linear Display P3, Rec.2020, Adobe RGB, ProPhoto RGB, HSL, HSV, HWB, HCT, CAM-family models, JzAzBz/JzCzHz and ICtCp. This list is illustrative, not a delivery commitment. An approachable selector label such as **Color space** may cover entries whose technical kinds, white points, encodings and appearance semantics remain distinct internally.
- **Built-in capability definitions.** A project-owned definition/catalog is the direction for describing identity, label, family, channels and their semantics/ranges, missing or powerless coordinates, editing geometries, planar axes and fixed coordinates, linear and polar editing where meaningful, serialization/output, and rendering/guide support. Framework components must consume capabilities instead of accumulating space-specific conditionals. A public third-party registry or plugin contract is not established here.

### Gamuts and visualization

- **Comparison is a set.** Ordinary inspection can check zero, one or several gamut references. Checked gamuts and visible guides/boundaries are independent selections: checking sRGB, Display P3 and Rec.2020 while drawing only sRGB and Display P3 is valid, as is selecting neither checks nor guides. A singular persistent `boundaryTarget` is not the vNext comparison model. Reserve **target** for a genuinely directional operation, such as mapping a color _to sRGB_ or producing output for a destination. Exact API names remain open.
- **Exact facts stay separate from pictures.** Authoritative gamut membership comes from color-domain analysis of the authored `ColorValue`. Sampled contours, ticks, tables, projected boundaries, guide positions and warning placement are presentation aids; none can decide exact membership, redefine the authored color or implicitly map it. Exact analysis may be supported for a space/gamut combination before a visual contour is available. Deterministic generated data remains appropriate for visualization where useful.

### One UI authority, several adapters

- **One instrument across frameworks.** Vue, React, later Svelte and later vanilla JavaScript must present the same product. Share the canonical anatomy/parts, presentation semantics, CSS, design tokens, icons, control geometry, state styling, motion, warnings, menus and framework-neutral interaction behavior wherever practical. Adapters primarily own lifecycle, reactivity, refs, component APIs, event emission and SSR/hydration integration. Byte-identical HTML is not required when a framework has a real need; avoid gratuitous divergence.
- **Framework-neutral UI package.** A future package conceptually equivalent to `@gamut-plane/ui` is the accepted shared authority for those concerns. Its precise boundary can evolve; likely contents include part names, presentation models, interaction/controller logic, icons, styles and instrument tokens. It must contain no Vue, React or Svelte components. Core retains color truth; render retains rendering/resource concerns. This ADR creates no package or public API.
- **One authored stylesheet.** vNext reverses v0.3's deliberate adapter-local style ownership. Every adapter uses one canonical Gamut Plane visual implementation rather than synchronized copies. A common part/state vocabulary, potentially `data-gp-part` and `data-*` state attributes, is accepted; exact attribute names are not fixed.
- **Self-contained library styling.** The instrument provides usable defaults and deliberate semantic customization hooks without requiring a consumer to install Maikel's site theme or personal design package. Semantic concepts include surfaces, text, muted text, borders, focus, status, control spacing/geometry and motion; this is not a final token list. Maikel's separate house-style layer may bridge these hooks in first-party demos, playgrounds, portfolio work, Scheme Tokens experiments, future apps and cross-framework examples. That house style does not become an external consumer dependency.
- **Open Props as replaceable infrastructure.** Open Props is a candidate primitive CSS-variable source, particularly for spacing, sizing, radii, easing, motion and perhaps typography scales. Project-owned semantic tokens sit between primitives and component CSS. Brand, surface, accent and status colors are authored deliberately, rather than inherited wholesale from its palette. Raw Open Props variable names are neither the pervasive component contract nor Gamut Plane's public design API. Adoption and import strategy remain open.

### Progressive interaction and enforceable parity

- **Small surface, deep capability.** Searchable/grouped representation selection, multiple gamut checks, independent guides, context-sensitive actions, exact numeric editing, serialization/copy choices, mapping, advanced inspection and precision/output settings belong behind progressive disclosure when secondary to ordinary picking. This does not fix menu layouts.
- **Accessible routes to actions.** Context menus are useful professional accelerators, but essential actions must also have discoverable keyboard and touch routes. Interaction and accessibility parity must be testable across adapters.
- **Evaluate headless primitives.** Zag.js may help share accessible menu, context-menu, popover, tooltip and select/listbox behavior through framework-neutral state machines. It is not an accepted dependency or mandate. A technical spike must establish its fit. Color-domain authority stays outside Zag, and working custom plane/channel gestures are not rewritten merely to use state machines.
- **Parity is evidence-based.** The end state must support deterministic equivalent Vue, React, Svelte and vanilla fixtures so CI can check part coverage, interaction, accessibility, responsiveness and visual parity. This is a future verification contract, not a claim that those adapters or tests exist today.

## Consequences and migration direction

The first implementation milestone should extract shared UI authority and framework parity while preserving v0.3 behavior and appearance as closely as practical. Space generalization, set-based gamut comparison, headless-primitives evaluation, additional adapters and redesign follow as independently testable changes rather than one rewrite. Migration may change existing public contracts, but this ADR does not specify their replacement signatures.

Preserve unless separately superseded: authored `ColorValue` and defining-versus-observed semantics; exact gamut analysis and explicit mapping; non-authoritative sampled guides; SSR/hydration support; a native React adapter rather than Vue wrapping; thin framework boundaries as the destination; renderer lifecycle/resource discipline; gesture commit, cancel and rollback semantics; accessibility; and deterministic generated visualization data where appropriate.

## Intentionally deferred

This decision does not fix final visuals, exact dimensions or component composition; package public APIs; the complete supported-space list or user-facing taxonomy; public registry/extensibility; names for gamut references and visible guides; Zag adoption or state machines for custom gestures; Open Props dependency/import strategy; the personal house-style package name; specific menu/dialog/popover primitives; Svelte/vanilla mechanics; mapping UI; or guide-data storage for every future space/gamut combination. Each needs implementation or design evidence and, where appropriate, its own decision.

## Relationship to ADR 0001

ADR 0001 remains the authority for the released two-plane behavior and for its defining-versus-observed, exact-status-versus-sampled-guide and interaction rules. Its two editable planes, singular `boundaryTarget` and adapter-local presentation are v0.3 scope, not permanent limits on vNext. This ADR accepts their future generalization and shared UI ownership without retroactively changing current behavior or the existing public API.
