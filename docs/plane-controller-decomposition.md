[ADR 0002](decisions/0002-vnext-instrument-architecture.md) sets the shared UI direction; [ADR 0001](decisions/0001-coordinate-plane-projections.md) and [architecture](architecture.md#interaction-lifecycle) set the current two-plane behavior. ## Scope and authority

The remaining duplication is the **temporary plane gesture**, not a second color model. Core's `projectColorToPlane` observes a `ColorValue`; `authorPlaneEdit` creates a definition in the edited plane and preserves observed alpha; `keyboardPlanePoint` owns step, Home/End and disc math; `PickerPlaneGeometry.constrainPoint` owns rectangular/disc bounds. `definingEquals` compares space, channels and alpha with `Object.is`, including signed zero. `PlaneEditReference` is an ephemeral hue direction for a hue-less neutral. These stay in `packages/core/src/picker/{edit,geometry,keyboard,plane}.ts` and `packages/core/src/color/value.ts`. The Canvas sampler is a separate `PickerPlaneFieldSampler`; a gesture controller must neither sample a field nor infer gamut membership.

Render's `fieldRenderer.ts` owns Canvas contexts, fallback, buffers, sampling, preview/full quality, cache keys and disposal. `geometry.ts` owns hydration-stable `pointStyle` and SVG path serialization. `pickerWarningPlacement.ts` and `planeInstrumentStyle.ts` own warning collision geometry and dimensions. `presentation.ts` owns gradient/connector serialization; `pickerPresentation.ts` combines core projections and **exact** gamut analysis with sampled presentation. `boundaryPresentation.ts` supplies the optional sampled target-guide point. The gesture consumes a constrained point and publishes an authored edit; it does not decide exact gamut status, place warnings, build contours or draw.

React's `mountPlane` is therefore **not** the proposed shared controller. ## Canonical pointer lifecycle and callback order

`idle` has no pointer, origin, expectation or pending frame. A qualifying `pointerdown` (no owner, and primary mouse button when `pointerType === "mouse"`) measures geometry. A null point leaves it idle. A valid point prevents default, stores **the exact current `ColorValue` object** as origin, takes that pointer ID, marks pointer focus, focuses the surface with `preventScroll`, requests capture, previews the point immediately and queues one RAF. No color callback runs at down. Both implementations reject a second active pointer by ID; neither rejects a non-primary touch/pen using `event.isPrimary`. A secondary mouse button is rejected.

During ownership, only the owner's moves matter. Each valid move replaces both `pending` and `latest`, moves the marker/warning before any color publication, and reuses the one queued frame. A frame clears its handle, then, if still mounted and owned, authors the latest pending point against the **current** accepted value and current edit reference. Successful authoring clears pending, records expected feedback and emits one live `update:modelValue` / `onValueChange`. Failed authoring restores the marker to the current projected value and emits nothing. The point may be outside an RGB gamut; only the core plane constraint applies. Fixed-axis changes, not same-plane visible-axis movement, invalidate the field.

`pointerup` for the owner chooses `pointFromPointer(up) ?? pending ?? latest`, in that order. It ends ownership first: cancel the RAF, clear pending/latest/origin/expected, release capture if held. It then authors and publishes the chosen final point **synchronously**, followed immediately by exactly one `commit` / `onValueCommit` with that same `ColorValue` object if authoring succeeded. Thus a click still publishes and commits; a queued move never overrides a usable up coordinate; a null up coordinate falls back to queued, then last seen/published point. An active gesture normally has a latest point because down required one. If no point or authoring fails, there is no commit. A later capture-loss or stale up event is inert. The new paired tests freeze publication order and both fallback cases; the existing two-plane tests freeze constrained final coordinates.

`pointercancel`, unexpected `lostpointercapture`, and Escape on the focused active surface take the rollback path. End/release/cancel the frame first, emit the **origin object itself** as a live change, reposition from that origin, then emit one cancel; never commit. The exact object preserves its defining space, alpha, missing components and signed zero. Escape prevents default and stops propagation only while a plane pointer gesture is active. Idle Escape remains available to the host. Blur removes pointer-focus attributes but does **not** end a drag. A supported arrow/Home/End during a drag interrupts without rollback and emits cancel, then performs its keyboard edit and emits change followed by commit if core authoring succeeds.

An authoritative different parent value ends ownership, drops pending work, releases capture, positions from the replacement and emits **cancel only**. It does not emit origin or a new edit. A changed plane does the same, positioning in the new plane while retaining the last accepted/published color; old points are never interpreted in the new plane. Unmount/disposal cancels frames, releases capture and detaches resources/listeners without any product callback. RAF callbacks guard disposed/ownership state. Vue's unmounted template removes its event handlers; React removes its native listeners explicitly.

## Controlled feedback and interruption

The comparison target is `expected ?? origin` in React and `latestInteractionColor ?? interactionOrigin` in Vue. Before the first successful publication it is the origin. After each publication it is the most recently authored color. Feedback with the same object or a separately allocated `definingEquals` definition acknowledges the gesture; object identity is not required. A different definition supersedes it **even if visually/observationally similar**. Since equality includes `Object.is` on channels and alpha, a signed-zero or alpha difference can interrupt. Both adapters read the latest parent-authored value when authoring the next point; neither keeps an independent persistent color model.

Delayed feedback is **not** versioned. If the parent returns an earlier publication after a newer one, it differs from the current expectation and interrupts. This is intentional current behavior to freeze, not permission to replay stale feedback in Phase 1B.4B. A replacement before the first frame compares with origin; one after publication compares with latest expected color; one with a queued point cancels the pending frame; one immediately before up makes the stale up inert. The paired tests cover queued replacement before/after first publication, stale earlier feedback and a redefinition in OKLab of the same observed color. Existing cloned-feedback tests cover defining-equal acknowledgment.

Vue's `flush: "sync"` prop watchers arbitrate when `props.modelValue` or `props.plane` becomes authoritative (`ColorPlane.vue` lines 394–408). React's `useCommitted` installs only committed props in a layout effect; a following layout effect calls `reconcile()` (`ColorPlane.tsx` lines 48, 81–105). Abandoned React renders cannot alter gesture callbacks. A parent's synchronous state update may therefore be observed at different framework integration times, while the tested transition outcome agrees after each framework has committed its input. Never make the shared controller read uncommitted React render props to erase this guarantee.

## View, keyboard, focus and accessibility

Vue's `defineModel("plane")` permits local or controlled view ownership; React's `useControllableView` uses `view ?? owned`, and a controlled request only calls `onViewChange`. An unaccepted controlled request leaves the actual plane unchanged and does not interrupt. An actual change before publication keeps origin; one after publication keeps the accepted live color; a queued point is discarded in both. Both emit cancel once, no rollback and no commit. The paired Vue host tests cover controlled/uncontrolled actual transitions, and the new React test covers before/after publication. A later up/lost-capture event from the old pointer is inert.

Keep keyboard handling in the adapters for 1B.4B. Both map ArrowLeft/Right/Up/Down/Home/End identically, use Shift as `coarse`, prevent default for handled movement, call core `keyboardPlanePoint` and `authorPlaneEdit`, then emit change + commit. Core owns step and disc/reference math; the adapter owns the focused key event, `preventDefault`, pointer-focus attributes and framework callback. Share **pointer gesture policy only**. A six-key mapping helper would save little and would couple keyboard lifecycle to a pointer controller without resolving an observed defect. Escape calls the shared gesture's rollback method only while owned. No global Escape listener is introduced.

The surface stays a tab stop with `role="application"`, a changing axis/current-value label, visible keyboard instructions and native controls outside it. Pointerdown adds both canonical `data-gp-pointer-focus` and legacy `data-pointer-focus`; keydown and blur remove both. Vue uses template events and React uses a native key listener plus JSX blur. Pointer focus state and `focus({ preventScroll: true })` belong in adapter integration; the shared controller needs only an `onPointerStart` port. The existing shared stylesheet owns focus-visible styling. This decomposition does not alter accessibility semantics; manual assistive-technology validation remains separate.

## Geometry and presentation seam

Both adapters normalize `clientX/Y` against the **content box** adjusted for border offsets and CSS scale, then call the active core plane's `constrainPoint`. Scroll capture marks bounds dirty and the next pointer event remeasures; resize remeasures immediately. Vue uses `useEventListener("scroll")` and `useResizeObserver`, React window listeners and `ResizeObserver`. Neither should rely on viewport dimensions. The controller should consume a `pointFromPointer(event): PlanePoint | null` port; the adapter owns measurement and its invalidation in 1B.4B. This avoids moving scroll/resize observer lifecycle into UI. A later UI DOM geometry helper is plausible only after deciding the currently different zero-layout fallback: Vue falls back from zero `clientWidth/Height` to rect dimensions and retains old local size for a zero rect; React uses client dimensions directly and zeroes local size. Normal rendered geometry is aligned, but this edge is **not proved equivalent** and must not be silently normalized during gesture extraction. Real-browser transformed/bordered geometry needs a dedicated paired fixture before a shared geometry helper.

Both implementations preview the marker and warning **on down/move before the RAF publication**. The gesture controller should call `onPreviewPoint(point)` synchronously. The adapter uses `pointStyle`/DOM style and `placePlanarWarning` with measured local surface size and target-guide obstacle. CSS mutations, warning dimensions, target-guide availability and connector geometry do not belong in the gesture state machine. Vue writes raw percentage strings on immediate preview; React uses `pointStyle`'s eight-decimal strings. Rendered position is equivalent at ordinary coordinates, but byte-identical preview style is not asserted. React's warning `targetGuideMarker: null` and Vue's `undefined` have the same absent-obstacle meaning. When accepted value or guide geometry changes, adapter presentation reconciliation can reposition independently of pointer arbitration.

The renderer receives `plane`, `fixed`, `pixelRatio`, and `interactionPreview`. **Plane dragging does not enable preview quality**. The OKLCH Hue native-range interaction toggles `interactionPreview`; only wide column-gradient fields with an available 192-column buffer use preview quality. Narrow fields or allocation failure draw full quality. The renderer's field key includes plane, size, DPR, fixed axis, capability and actual quality; visible-axis edits reuse the field. Vue's watchers schedule a field RAF on plane/fixed-axis, preview or DPR change, and VueUse observes resize/DPR. React's `fieldInput` reconciliation schedules a field RAF; its native resize, media-query, scroll and window integration remain in a React-owned resource binding. `createFieldRenderer`, capability notifications, quality state, field RAF, context negotiation, draw, ResizeObserver, resolution media query and disposal must stay outside UI's plane gesture controller. Core's `PickerPlaneFieldSampler` stays a renderer input, never a gesture input.

## Proposed private UI API and direct tests

Create a private `packages/ui/src/interaction/planeGesture.ts` with a mount-time DOM binding. Its types can be generic over authored value and point so UI keeps **no core or render runtime dependency**. The concrete shape should be close to:

```ts
interface PlaneGestureInput<Value, Point, View> {
  value: Value;
  view: View;
  pointFromPointer(event: PointerEvent): Point | null;
  authorPoint(value: Value, point: Point): Value | null;
  definingEquals(left: Value, right: Value): boolean;
  onPointerStart(): void; // adapter focus and pointer-focus state
  onPreviewPoint(point: Point): void; // adapter marker/warning presentation
  onValueChange(value: Value): void;
  onCommit(value: Value): void;
  onCancel(): void;
  onRestorePresentation(value: Value): void;
}

interface PlaneGestureBinding {
  reconcile(): void; // current authoritative value/view after framework commit
  rollback(): void; // focused Escape or native cancellation; silent if idle
  interrupt(): void; // keyboard takeover; cancel without origin publication
  dispose(): void; // callback-silent
}

function mountPlaneGesture<Value, Point, View>(
  surface: HTMLElement,
  current: () => PlaneGestureInput<Value, Point, View>,
): PlaneGestureBinding;
```

This is a proposed **internal** port contract, not a public API. For a real implementation, use a stable view identity (the current plane descriptor), and keep `current()` committed in React. The adapter's `authorPoint` closes over core's plane ID and current `PlaneEditReference`; `pointFromPointer` closes over the adapter geometry and `plane.constrainPoint`. `onRestorePresentation` should be invoked on interruption/rollback or failed authoring, not used as a second color authority. A narrower port may combine it with `onPreviewPoint` after projecting the selected value in the adapter. Keep pointer event attachment/capture and one-shot RAF in this DOM-specific controller, but no key mapping, CSS selector, Canvas object, render constants, observer or framework ID. Avoid a boolean `cancel(rollback)` public method: named transitions make callback consequences reviewable. If a callback synchronously feeds back during publication, the controller must set expected state **before** invoking it, as both current adapters do.

Add direct controller tests in `packages/ui/test/planeGesture.test.ts` using Vitest and jsdom already present in the workspace. A UI-local Vitest config and explicit UI dev dependencies on the already pinned Vitest/jsdom versions are the smallest future setup; Phase 1B.4A adds neither dependency nor UI test file. Use fake RAF and a host element with capture stubs; drive ports with opaque values and points. Assert exact transition logs, point priority, reentrant parent feedback, expected/defining-equal feedback, stale feedback, view interruption, rollback object identity, capture release and silent disposal. Keep Canvas, warning math and screenshots in existing render/adapter suites. Add a real-browser capture/geometry check in paired packed consumers if the extracted DOM binding changes event handling.

## Non-goals and open questions

Phase 1B.4B should not change `ColorValue`, projections, `authorPlaneEdit`, keyboard math, gamut tables, warning-placement math, field rendering, public adapter APIs, authored CSS, anatomy, Svelte/vanilla support, or the vNext product design. It should not move `createFieldRenderer`, Canvas status, ResizeObserver or DPR observation to UI. The only unresolved extraction decisions are the exact internal port names, whether pointer-focus/focus is one or two adapter callbacks, whether a later shared geometry helper is warranted, and the behavior when browser pointer capture is unavailable. Those questions have bounded owners and tests above; none requires rediscovering the current gesture lifecycle.
